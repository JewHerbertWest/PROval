## Структура проекта

Проект представляет собой программную реализацию переработанной архитектуры системы управления шлюзами космической станции «Севастополь». В коде отражены основные элементы архитектуры: входные интерфейсы, интерфейс фильтрации команд, центральная система управления, подсистемы контроля отсеков, доступа, шлюзов, стыковки, мониторинга, аварийного реагирования, хранилище данных и сервис журналирования.

В текущей реализации проект собран как одно FastAPI-приложение, внутри которого каждый элемент архитектуры вынесен в отдельный Python-модуль. Такой вариант позволяет показать логику взаимодействия компонентов, негативные сценарии и работу защитных элементов без разворачивания большого количества отдельных микросервисов.

## Входные интерфейсы

### interfaces.py

Файл `components/interfaces.py` реализует входные точки системы. Через них команды поступают от оператора станции, экипажа, Земли и внешнего корабля.

В этом файле реализованы следующие компоненты:

| Компонент               | Назначение                                         |
| ----------------------- | -------------------------------------------------- |
| `LocalOperatorTerminal` | Имитирует локальный операторский терминал станции. |
| `CrewControlPanel`      | Имитирует пульт управления экипажа.                |
| `EarthInterface`        | Имитирует интерфейс связи с Землёй.                |
| `ShipInterface`         | Имитирует интерфейс связи с кораблями.             |

Эти компоненты не должны напрямую выполнять критические операции. Их задача — принять входящую команду и передать её в интерфейс фильтрации команд.

| Метод                     | Тип запроса | Назначение                                                                       |
| ------------------------- | ----------- | -------------------------------------------------------------------------------- |
| `/terminal/open_airlock`  | POST        | Отправка команды открытия шлюза через локальный операторский терминал.           |
| `/terminal/unlock_sector` | POST        | Отправка команды разблокировки сектора через локальный терминал.                 |

| `/earth/send_command`     | POST        | Передача команды от Земли. Используется, в том числе, для НС-1.                  |
| `/earth/replay_command`   | POST        | Повтор ранее отправленной команды от Земли. Используется для НС-14.              |
| `/ship/docking_request`   | POST        | Передача запроса на стыковку от внешнего корабля. Используется для НС-2 и НС-15. |

## Интерфейс фильтрации команд

### command_filter.py

Файл `components/command_filter.py` реализует интерфейс фильтрации команд. Это один из ключевых элементов переработанной архитектуры. Он принимает команды от внешних интерфейсов и проверяет их перед передачей в центральную систему управления.

Фильтрация включает несколько этапов:

```text
проверка криптографической обработки;
проверка политик безопасности;
проверка маршрута через монитор безопасности команд;
проверка авторизации источника;
валидация команды.
```

Если хотя бы одна проверка не пройдена, команда блокируется и не передаётся в ЦСУ.

## Политики безопасности

### policies.py

Файл `components/policies.py` содержит правила, по которым система принимает решение о допустимости команды или операции.

В проекте используются два типа политик:

```text
1. Политики маршрутов — проверяют, может ли один компонент обратиться к другому.
2. Политики операций — проверяют смысл команды: можно ли открыть шлюз, разрешён ли доступ, нет ли конфликтующих команд.
```

Политики маршрутов работают по принципу белого списка. Если пары `source → deliver_to` нет в списке разрешённых маршрутов, обращение блокируется.

Пример логики:

```python
def check_operation(id, details) -> bool:
    src = details.get("source")
    dst = details.get("deliver_to")

    if not all((src, dst)):
        return False

    return {"src": src, "dst": dst} in policies
```

## Монитор безопасности команд

### security_monitor.py

Файл `components/security_monitor.py` реализует монитор безопасности команд. Он проверяет, не нарушает ли команда допустимый маршрут взаимодействия и не является ли она повторной.

Монитор используется для защиты от ситуаций, когда компонент пытается обратиться туда, куда он не должен обращаться по архитектуре. Также он участвует в защите от повторного выполнения старых команд.

## Центральная система управления

### central_control.py

Файл `components/central_control.py` реализует центральную систему управления станции. ЦСУ получает только те команды, которые прошли фильтрацию.

ЦСУ не должна сразу выполнять опасные действия. Перед открытием шлюза она обращается к другим компонентам:

```text
к сервису контроля отсеков;
к подсистеме контроля доступа;
к политикам безопасности;
к сервису управления шлюзами;
к сервису журналирования.
```

### API

| Метод                              | Тип запроса | Назначение                                    |
| ---------------------------------- | ----------- | --------------------------------------------- |
| `/central/open_airlock`            | POST        | Обработка команды открытия шлюза.             |
| `/central/docking`                 | POST        | Обработка запроса на стыковку корабля.        |
| `/central/conflicting_commands`    | POST        | Проверка сценария с конфликтующими командами. |
| `/central/delayed_emergency_close` | POST        | Проверка сценария задержки аварийной команды. |

## Сервис контроля отсеков

Этот компонент используется в сценариях, где важно подтвердить, что открытие шлюза не приведёт к разгерметизации или другой опасной ситуации.

### API

| Метод                 | Тип запроса | Назначение                                |

| `/compartments/check` | POST        | Проверка давления и герметичности отсека. |

## Подсистема управления шлюзами

Подсистема управления шлюзами не должна выполнять команду, если не выполнены условия безопасности.

## Аварийный модуль

### emergency_module.py

Файл `components/emergency_module.py` реализует аварийный контур. Он отвечает за переход системы в безопасный режим, закрытие шлюзов и блокировку опасных операций.

В переработанной архитектуре аварийная реакция не должна полностью зависеть от ЦСУ. Поэтому при критическом событии аварийный модуль может инициировать безопасное состояние системы.

### API

## Исполнительные устройства

### devices.py

Файл `components/devices.py` реализует имитацию исполнительных устройств станции. К ним относятся приводы шлюзов, блокировки доступа и другие устройства, которые должны выполнять только проверенные команды.

Исполнительные устройства не принимают самостоятельных решений о безопасности. Они получают команды от защищённых компонентов архитектуры.

## Тесты

### tests/test_negative_scenarios.py

Файл `tests/test_negative_scenarios.py` содержит 17 негативных сценариев. Каждый сценарий проверяет попытку атаки на один из элементов системы.

Особенность этих тестов в том, что они проверяют именно успешность атаки:

```text
атака прошла — тест зелёный;
атака не прошла — тест красный.
```

Для переработанной защищённой архитектуры ожидаемый результат — падение всех 17 НС-тестов. Это означает, что атаки не смогли нарушить цели безопасности.

### Запуск тестов

```bash
pip install -r requirements.txt
pytest
```

Ожидаемый результат:

```text
17 failed
```

Такой результат является корректным для защищённой архитектуры, потому что тесты написаны как попытки успешной атаки.

## Запуск проекта

Перед запуском необходимо установить зависимости:

```bash
pip install -r requirements.txt
```

Пример локального запуска:

```bash
uvicorn app:app --reload
```

После запуска приложение доступно по адресам:

```text
http://localhost:8000
http://localhost:8000/docs
```

Также проект можно запустить через Docker:

```bash
docker compose up --build
```
